# Cash Settlement Query Service Design

## Summary

This source is a preliminary database design for the Cash Settlement Query Service. It defines two wide, denormalized PostgreSQL tables:

- `cashflow_data`, which appears intended to support current-state cashflow queries.
- `cashflow_data_history`, which appears intended to retain historical cashflow records.

The source is authoritative for the proposed table structures only. It does not define ingestion, update or upsert rules, history movement, retention, indexes, access controls, API contracts, ownership, or performance requirements.

## Data model

Both tables flatten cashflow, trade, entity, portfolio, instrument, settlement-instruction, payment-routing, workflow, and data-provenance attributes into a single record. The field prefixes identify broad source domains, including `cashflow__`, `trade__`, `entity__`, `portfolio__`, `instrument_common__`, `ssi__`, and `data_flow__`.

The schema contains multiple potentially overlapping identity and version fields, including `id`, `cashflow_id`, `cashflow__cashflow_id`, `cashflow_index`, cashflow business and technical versions, minor versions, audit versions, and `trade__trade_version`. Only `id` is constrained as a primary key.

Most text fields are nullable and many also default to the empty string. The design therefore permits both `NULL` and `''` as representations of absent data. Several temporal and numeric-looking values are stored as `text`, including payment amount and cutoff fields.

The tables include sensitive settlement-instruction data such as account numbers, BIC codes, names, addresses, remittance information, and sender-to-receiver information. The source does not specify masking, encryption, authorization, audit logging, or retention controls.

No secondary indexes, foreign keys, check constraints, or unique business-key constraints are included in the supplied DDL.

## Current and history semantics

The table names suggest a current-state and history separation, but the source does not establish the lifecycle contract. In particular, it does not state whether:

- History is append-only.
- A current record is copied before an update.
- All source events or only selected changes are retained.
- History is ordered by source event, cashflow version, audit version, or timestamp.
- `id` is stable between current and historical records.
- Out-of-order, duplicate, corrected, or replayed events are handled.

These questions are tracked in [[what-is-the-authoritative-current-and-history-lifecycle-for-cashflow-data]] and [[what-is-the-canonical-cashflow-storage-and-history-model]].

## Limitations and follow-up

This design should not be used alone to infer production deployment, query performance, event-processing behavior, or data-retention guarantees. The canonical identity/version contract, current/history lifecycle, workload-driven indexes, retention policy, and sensitive-data controls require separate decisions.

See [[denormalized-cashflow-query-read-model]] for the design pattern, [[cash-settlement-cashflow-read-model]] for the broader read-model context, and [[postgresql]] for the database platform context.
