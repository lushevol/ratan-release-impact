# FX Cashflow Status Write Back - Razor to Stella

This functional requirement specifies an FMRP Drop 2 (2024) design for returning eligible FX cashflow statuses from [[razor]] to [[stella]] through [[ratan]]. It applies to FX Spot, Forward, and Swap cashflows processed in Razor because of stated Stella settlement-method limitations.

The intended control is duplicate-payment mitigation. Razor is the processing authority for the in-scope payment; Stella receives a `SUSPENDED-MATURED` status to support its FX hard-block logic. This is a proposed design specification, not evidence that the control was deployed or reconciled in production.

## Scope and processing flow

- Trade replication: `Stella → RATAN → Razor`
- Cashflow-status feedback: `Razor → RATAN → Stella`
- Target Stella status: `SUSPENDED-MATURED`
- Target delivery: FMRP Drop 2, 2024

Eligible Razor cashflow validation states are `Released`, `Settled`, `Netted`, `Split`, and `CCPNetted`. Eligible reverse states are `None` and `Correction`. RATAN must not process a Razor cashflow ID that has already completed successfully.

Resultant cashflows created by netting or splitting are excluded from write-back. Un-net and un-split events are also excluded, as is a withdrawal-only event. A write-back that would leave Stella at `SUSPENDED-MATURED` is intended to be avoided.

## RATAN processing logic

```text
For FX replication cashflow from Stella:
- Save trade ID, trade version, and the 6 economic fields.
- Compare the latest-version cashflow for the same trade ID with the prior cashflow on the 6 fields.

If Non-Eco amendment:
  If previous cashflow status is SUSPENDED-MATURED:
    Update Stella latest new cashflow status to SUSPENDED-MATURED.
  Else if previous cashflow status is SUSPENDED:
    Wait for Razor cashflow.

If new-only or economic amendment:
  Wait for Razor cashflow.

For FX replication cashflow from Razor:
  If:
    cashflow validation status in (Released, Settled, Netted, Split, CCPNetted)
    AND reverse status in (None, Correction)
    AND the same Razor cashflow ID has not previously processed successfully:
      Map to Stella latest new cashflow using the 6 economic fields.
      If all fields match:
        Update Stella latest new cashflow status to SUSPENDED-MATURED.
      Else:
        Store the NACK in RATAN for phase 1.

If withdrawal only:
  Ignore.
```

The six economic fields are Booking Entity, Counterparty, Currency, Amount, Value Date, and Pay/Receive. See [[six-economic-field-cashflow-matching]].

## Stated Stella behavior

FX cashflows generated by [[tds3]] are stated to default to `Suspended` and not be sent down. Fee-related cashflows are an exception and are `Projected` for separate RATAN processing. Fee-related release or settlement is not required for hard block.

The requirement states that a user cancellation or update of a trade with a `SUSPENDED-MATURED` cashflow automatically lifts the hard block until a new cashflow reaches `SUSPENDED-MATURED`. For a trade with two cashflows, one `SUSPENDED-MATURED` cashflow is stated to be sufficient to hard-block the trade. See [[stella-suspended-matured-hard-block]].

## Matching limitations

Razor does not provide a trade version. RATAN therefore selects the latest Stella cashflow version for the trade and applies six-field matching. Currency matching compares only the first two code characters to accommodate the stated `CNY` to `CNH` conversion. Amount matching accepts a difference “within the decimal” for non-JPY and within 100 for JPY.

These are intentionally non-exact matching rules. The source identifies a false-match risk for unknown `CN*` currencies and does not define the non-JPY tolerance formula. The interface table's `CNO` Stella currency example differs from the narrative's `CNY` example.

## Control gaps

The source does not define a reconciled operational control for unmatched, duplicate, delayed, or concurrent messages. It also uses inconsistent forms of the target status: `SUSPENDED-MATURED` and `SUSPEND-MATURED`. The latest-version strategy, fuzzy currency comparison, and amount tolerances can produce an incorrect cross-system match without specified compensating controls.
