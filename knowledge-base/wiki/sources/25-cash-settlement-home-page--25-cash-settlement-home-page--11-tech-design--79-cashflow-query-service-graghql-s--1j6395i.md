# Cashflow Query Service - GraghQL schema and DB column mapping for dynamic query

## Summary

This technical-design proposal attributes UI and Query Service filter mismatches to independently maintained field mappings. It proposes [[rule-service]] as the versioned central authority for logical-model-to-XPath mappings, with [[query-service]] consuming mappings through [[ratanone-foundation]] instead of maintaining local XPath configuration.

The document also proposes JSONB-based querying and indexing for Query Service. It does not define the GraphQL schema, Rule service API, JSONB expressions, indexes, authorization controls, migration approach, or performance evidence. Therefore, it is design intent rather than an approved or validated implementation contract.

## Proposed responsibilities

| Module | Proposed changes |
|---|---|
| Rule service | Expose logical-model-to-XPath mappings by version and context; version XPath data; optionally publish data-version-upgrade events. |
| Query service | Remove locally maintained XPath mappings; transform through the SDK; query and index JSONB. |
| SDK (`ratanone-foundation`) | Provide a predefined mapping file and version; transform SCBML into logical-model JSON; optionally retrieve mappings by version and `RATAN_DATA` / `CASHFLOW_DATA` context; optionally cache active mappings; optionally refresh from a scheduled interval or version-upgrade event. |

## Mapping convention

The stated default logical-field-to-column convention is:

1. Replace `.` with `__`.
2. Replace `Settlement_Instruction` with `ssi`.
3. Convert to lowercase.

This convention has explicit exceptions and incomplete entries, so it must not be treated as a complete canonical contract without reconciliation. See [[dynamic-cashflow-query-field-mapping]].

## Open design issues

- The design calls Rule service authoritative while also describing a local predefined mapping file. Precedence during version lag or service outage is unspecified.
- “Latest version” is not reconciled with retrieval by explicit version and context.
- The inventory has two unmapped Instrument fields and multiple candidate duplicate or unused columns.
- JSONB querying is proposed but lacks physical design, query-plan, performance, input-validation, entitlement, and masking evidence.
- The title refers to GraphQL schema mapping, but no GraphQL types, filters, operators, nullability, enums, or authorization rules are provided.
