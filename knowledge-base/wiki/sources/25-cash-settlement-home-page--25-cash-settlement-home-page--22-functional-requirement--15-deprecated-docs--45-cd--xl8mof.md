# CDU Trade Confirmation Notification and Cashflow

> **Status:** Deprecated functional requirement. This page records a design proposal and illustrative scenarios, not evidence of implementation or production validation.

## Purpose

The document proposes a mechanism for using trade affirmation and confirmation status from [[cdu]] to control cashflow straight-through processing in [[ratan]]. Ratan is expected to consume CDU trade-confirmation notifications, identify the corresponding cashflows, and release them to STP only when the trade and cashflow linkage is sufficiently current.

The requirement was requested by FMO. When a confirmation notification is received, the message must contain identifiers that allow Ratan to locate the relevant cashflow or cashflows.

## Candidate identifiers

### Trade ID

- Logical Model Path: `Trade.Trade_Id`
- SCBML Path:

```text
/scb:SCBML/scb:payload/scb:FPMLPayload/conf:trade|/scb:SCBML/scb:payload/scb:FPMLPayload/*/(*:originalTrade|*:trade))/conf:tradeHeader/conf:partyTradeIdentifier[conf:partyReference/@href="party1"]/conf:tradeId[@tradeIdScheme="http://www.sc.com/coding-scheme/tradeId"]
```

Trade ID identifies the continuing trade but does not, by itself, identify the current cashflow version.

### Tracking Version

- Logical Model Path: `Trade.Tracking_Version`
- SCBML Path:

```text
/scb:SCBML/scb:payload/scb:FPMLPayload/scb:header/scb:process/scb:trackingVersion
```

Tracking Version increases across trade actions, including updates. The proposed initial rule was:

```text
tracking_version(trade) >= tracking_version(cashflow)
```

This comparison is insufficient when an amended cashflow is missing from Ratan because an older cashflow can still satisfy the inequality.

### Event ID

- Logical Model Path: `Trade_Event.Event_Id`
- SCBML Path:

```text
/scb:SCBML/scb:payload/scb:FPMLPayload/scb:header/scb:process/scb:eventId[@eventIdScheme="http://www.sc.com/coding-scheme/eventId"]
```

Event ID provides event-lineage information. It can remain constant across economic trade updates while new cashflow versions are generated, and it can change for a non-economic amendment. It is therefore not a complete freshness key.

## Normal-case scenario

The initial proposal treated a cashflow as eligible when the confirmed trade tracking version was greater than or equal to the cashflow tracking version.

| Trade ID | Trade Business Event | Trade Action Type | Trade State | Tracking Version | Cashflow ID | Cashflow Event | Cashflow Business Version | Cashflow Version |
|---|---|---|---|---:|---|---|---:|---:|
| 3384504064 | Trade | Book | TOBESENT | 0 | C1 | New | 0 | 0 |
|  |  |  |  |  | C2 | New | 0 | 0 |
|  | Trade | Book | SENT | 1 |  |  |  |  |
|  | Trade | Update | TOBESENT | 2 | C1 | Amendment | 1 | 1 |
|  |  |  |  |  | C2 | Amendment | 1 | 1 |
|  | Trade | Update | SENT | 3 |  |  |  |  |
|  | Trade | Update | CONFIRMED | 4 |  |  |  |  |

In this example, the latest confirmed trade has tracking version `4`, while the amended cashflows were generated at version `1` and associated with the update at tracking version `2`.

## Missing-cashflow exception

The source identifies a failure mode in which:

1. CDU confirms the updated trade at tracking version `4`.
2. Ratan has only the original cashflow `C1` at version `0`.
3. The amended cashflow generated by the update at tracking version `2` is missing.
4. Ratan could incorrectly use the `CONFIRMED` notification to release the stale original cashflow.

This demonstrates that version ordering does not prove version completeness or cashflow validity.

## Proposed Reference ID control

The proposed resolution introduces a linkage Reference ID:

1. Persist the Reference ID in both trade SCBML and cashflow SCBML.
2. Change it only when an economic trade update affects cashflows.
3. Keep it unchanged for status transitions and non-economic changes.
4. For cashflows generated by a fixing event, obtain the Reference ID from the parent trade and enrich the generated cashflow SCBML.
5. Compare the Reference ID in the CDU confirmation notification with the Reference ID on the latest available cashflow.
6. If the values differ, do not release the cashflow to STP. Raise an exception for FMO Ops users.

Illustrative values:

| Trade action | Tracking Version | Reference ID | Cashflow ID | Cashflow Version | Cashflow Event |
|---|---:|---:|---|---:|---|
| Book | 0 | 101 | C1, C2 | 0 | New |
| SENT | 1 | 101 |  |  |  |
| Update | 2 | 102 | C1, C2 | 1 | Amendment |
| SENT | 3 | 102 |  |  |  |
| CONFIRMED | 4 | 102 |  |  |  |

If the confirmation carries Reference ID `102` but Ratan’s latest available `C1` carries Reference ID `101`, the proposed result is:

```text
Reference ID mismatch => do not STP C1 + version 0; raise an operational exception
```

The document does not define the Reference ID format, generation authority, uniqueness scope, persistence contract, or behavior for cancellation, reversal, retransmission, or other lifecycle events.

## Evidence and limitations

The document clearly identifies the logical gap in relying on confirmation status and a lower-or-equal tracking version. The Reference ID is presented as a stronger design proposal, but the source contains no implementation, testing, or production-validation evidence.

Because the document is located under `Deprecated docs`, it should not be treated as the current authoritative contract without corroboration from newer requirements or implementation documentation.
