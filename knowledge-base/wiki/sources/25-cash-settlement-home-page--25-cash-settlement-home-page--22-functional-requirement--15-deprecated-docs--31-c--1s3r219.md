# Cashflow Events Control Draft 1

> **Historical and deprecated source.** This document is a Draft 1 functional design and should not be treated as the authoritative current-state specification without corroboration from newer requirements, implementation documentation, or production evidence.

## Scope

The draft describes cashflow events generated by [[entities/stella]] from trade market events and processed by [[entities/ratan]]. It covers:

- `New` cashflows created by trade booking, observation, or fixing events.
- `Withdrawal` events that cancel an existing cashflow.
- `Amendment` events that update selected attributes before netting, release, or settlement.
- `Withdrawal & New` events that replace a cashflow after it has progressed beyond the amendment boundary.
- Automatic un-netting and un-splitting.
- NSTP controls intended to prevent duplicate payments.
- Murex reversal and replacement flows.
- Value-date expiry and physical-status versioning.

The draft references [[entities/murex-2-11]], [[entities/fmrp]], [[entities/scbml]], and [[entities/fmsre]].

## Event classification

The proposed classification is:

| Cashflow event | Draft meaning | Proposed applicability |
|---|---|---|
| `New` | A cashflow generated by a trade lifecycle event, such as a new trade booking or an observation/fixing event | Any newly generated cashflow |
| `Withdrawal` | A cancellation driven by a trade market event | Existing cashflows that must be cancelled |
| `Amendment` | An update to amount, currency, date, counterparty, booking entity, payment type, or settlement method | Before the cashflow reaches `NETTED`, `RELEASED`, or `SETTLED` |
| `Withdrawal & New` | Withdrawal of the existing cashflow followed by creation of a replacement cashflow | When the original cashflow has reached `NETTED`, `RELEASED`, or `SETTLED` |

The central design boundary is the lifecycle position of the existing cashflow. Before the boundary, the draft proposes an in-place amendment or cancellation. After the boundary, it proposes a withdrawal and replacement pattern.

## Withdrawal behavior

For an early-stage gross cashflow, the draft shows the original lifecycle being closed:

```text
New:
PROJECTED -> QUEUED -> WAITING -> READY

Withdrawal:
PROJECTED -> CANCELLED
```

The examples increment the business and cashflow versions from `0` to `1`. The source contains the spelling `PROJECTECD` for the Stella status in some examples; this is retained as source terminology but should not be treated as a valid status enum.

For a cashflow already in `RELEASED` or `SETTLED`, the draft shows a withdrawal row with a complete processing lifecycle:

```text
PROJECTED -> QUEUED -> WAITING -> READY -> RELEASED -> SETTLED
```

The document does not establish whether this represents a reversal payment, a compensating accounting entry, a manual operation, or only a control record.

## Netting component withdrawal

The draft describes a netting relationship with components `C101`, `C102`, and `C103` and resultant `N101`:

| Cashflow type | ID | Event | Business version | Cashflow version | Ratan version | Currency | Pay/Receive | Amount | Status |
|---|---|---|---:|---:|---:|---|---|---:|---|
| Netting component | C101 | New | 0 | 0 | 3 | USD | Pay | 100 | `PROJECTED -> QUEUED -> WAITING -> NETTED` |
| Netting component | C102 | New | 0 | 0 | 3 | USD | Receive | 150 | `PROJECTED -> QUEUED -> WAITING -> NETTED` |
| Netting component | C103 | New | 0 | 0 | 3 | USD | Pay | 200 | `PROJECTED -> QUEUED -> WAITING -> NETTED` |
| Netting resultant | N101 | New | 0 | 0 | 2 | USD | Pay | 150 | `QUEUED -> WAITING` |

When `C101` is withdrawn, the draft proposes:

- `C101` moves to `CANCELLED`.
- `C102` and `C103` are automatically un-netted and return to `QUEUED -> WAITING`.
- `N101` moves to `DEAD` when the resultant is still in Ratan.
- When `N101` is outside Ratan, Ratan generates a withdrawal event with an updated business version. Operations may need to inspect FMSRE, manually release the resultant, and send `MT192`/`MT202`.

The source does not define the netting sign convention explaining the resultant amount of `150`.

## Split cashflow withdrawal

The split example uses gross cashflow `C101` and children `S101` and `S102`:

| Cashflow type | ID | Event | Business version | Cashflow version | Ratan version | Currency | Pay/Receive | Amount | Status |
|---|---|---|---:|---:|---:|---|---|---:|---|
| Gross cashflow | C101 | New | 0 | 0 | 3 | USD | Pay | 200 | `PROJECTED -> QUEUED -> WAITING -> SPLIT` |
| Split cashflow | S101 | New | 0 | 0 | 2 | USD | Pay | 100 | `PROJECTED -> QUEUED -> WAITING` |
| Split cashflow | S102 | New | 0 | 0 | 2 | USD | Pay | 100 | `PROJECTED -> QUEUED -> WAITING` |

For withdrawal:

- The parent `C101` moves to `CANCELLED`.
- Children still in Ratan move to `DEAD`.
- Children outside Ratan receive Ratan-generated withdrawal events with updated business versions.

The draft does not specify the parent-child correlation key, partial child processing behavior, or whether released children require a financial reversal.

## Amendment behavior

For a cashflow in `PROJECTED`, `QUEUED`, `WAITING`, or `READY`, the draft proposes retaining the cashflow ID and applying the latest event:

| Cashflow ID | Event | Business version | Cashflow version | Amount | Ratan status |
|---|---|---:|---:|---:|---|
| C101 | New | 0 | 0 | 100 | `PROJECTED -> QUEUED -> WAITING -> READY` |
| C101 | Amendment | 1 | 1 | 150 | `PROJECTED -> QUEUED -> WAITING -> READY` |

This implies versioned replacement of the amount while preserving `C101`. The retention, supersession, ordering, and discard rules for prior versions remain unspecified.

## Withdrawal and New ordering

For Stella messages that contain withdrawal and new events together, the draft states that the events are represented as separate events with individual [[entities/scbml]] records. It proposes a full NSTP rule so that the replacement event cannot be sent or released before withdrawal processing completes.

For an early-stage cashflow, the example is:

```text
C101 New        -> PROJECTED -> QUEUED -> WAITING
C101 Withdrawal -> PROJECTED -> QUEUED -> WAITING
C102 New        -> PROJECTED
```

For released or settled cashflows, the explicit control is:

```text
Withdrawal of C101 must proceed before new cashflow C102.
```

This ordering is intended to mitigate duplicate-payment risk.

## Separate-message scenarios

The draft identifies two separate-message cases:

1. A Stella amendment where cashflow matching fails under the FMRP matching logic.
2. A Murex amendment after the original cashflow has been sent from Murex 2.11 to Ratan with payment workflow status `SNTR`.

For the Murex case, the amendment produces:

- A reversal of the original cashflow.
- A new cashflow for the amended trade.
- `Murex Reversal Flag`.
- `Murex Amendment Flag`.

The draft proposes setting Murex amendment replacements to full NSTP because the expected volume is considered acceptable. It separately states that a Stella replacement new cashflow may be STP in some separate-message cases. The Murex-specific control must not be generalized to Stella or Korea `COMP` flows without additional evidence.

## Expiry and physical-status versioning

The expiry model distinguishes Stella physical status from the prior Ratan processing record:

1. Stella creates a `New` cashflow with business version `0`, cashflow version `0`, and physical status `Live`.
2. Ratan processes the cashflow, potentially to `FAILED`, `RELEASED`, `SETTLED`, `NETTED`, or `SPLIT`.
3. On `VD+1`, Stella creates a later cashflow version with physical status `Dead`.
4. Ratan filters out the expiry version and continues operating on the previous Ratan record.

Example for a failed cashflow:

| Cashflow ID | Event | Business version | Cashflow version | Ratan version change | Ratan status |
|---|---|---:|---:|---|---|
| C101 | New | 0 | 0 | `0 -> 1 -> 2 -> 3` | `PROJECTED -> QUEUED -> WAITING -> FAILED` |

For released, settled, netted, or split records, Stella may create successive versions whose physical status remains `Live` until the final expiry version becomes `Dead`. The draft says Ratan must filter out the new expiry record and continue working on the previous record.

## Reliability and limitations

The source provides detailed historical examples but has limited authority:

- It is stored under `Deprecated docs`.
- It is explicitly a draft.
- Status names contain typographical inconsistencies such as `PROJECTECD`, `RELASED`, `RELEAESD`, and `CANCELLD`.
- Version changes are not consistently explained.
- Ownership of Stella status, physical status, and Ratan status is unclear.
- “Out of Ratan” is not defined.
- Post-release and post-settlement withdrawal behavior is not operationally complete.
- Manual FMSRE and SWIFT actions are presented as draft operational possibilities rather than confirmed requirements.
