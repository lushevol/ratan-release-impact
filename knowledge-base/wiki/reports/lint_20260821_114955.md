# Semantic Lint Report — Settlement Platform Wiki

## Scope
Audited 3 summaries, 6 concept pages, 6 entity pages, 3 source documents, and `index.md`. The wiki is small but coherent: all three sources (service catalog, operations runbook, release overview) describe the same four-service settlement pipeline, and the derived concept/entity pages are mostly well-synthesized and consistently cross-linked. No explorations exist (fine — they are optional). Findings below, ordered by severity.

---

## 1. Contradictions

**Minor — Retry budget scope is over-generalized.**
- `concepts/retry-budget.md` claims: *"In the [[summaries/release-overview]], **each service** applies a retry budget of three attempts for transient downstream failures."*
- But the source (`summaries/operations-runbook.md` / `sources/operations-runbook.md`) attributes retrying specifically to **Orchestration**: *"For a transient timeout, Orchestration may retry up to three times."* The release overview says only "a retry budget of three attempts" without attributing it to each service.
- This is a mild overreach: the concept page implies every service retries its own downstream calls, which is not stated anywhere. Recommend rewording to "a shared retry budget of three attempts, applied by Orchestration for transient downstream failures" to match the sources.

**Minor — "Correlation IDs introduced by the release" vs. pre-existing correlation contract.**
- `summaries/release-overview.md` and `entities/ratan.md` say the 2026.08 release *introduces* correlation IDs across every service.
- `summaries/service-catalog.md` (which describes the same four services) already mandates `X-Correlation-Id` on every request as a shared contract.
- Not a hard contradiction, but the "introduced by this release" framing sits uneasily with a catalog that already treats the header as standard. Worth a clarifying sentence (e.g., the release extended end-to-end propagation/observability on top of an existing header).

No other factual contradictions found across concept and entity pages; service ordering (Netting → SSI Stamping), the `case.completed` publish-after-persistence rule, the three-retry/validation-error distinction, idempotency-record escalation, and the rollback procedure are all mutually consistent.

## 2. Gaps

**Minor — "Observability" theme has no concept page.**
- All three documents converge on observability as a core goal: correlation IDs for end-to-end tracing, the dashboard (queue age, failed batches), timestamp comparison, and post-incident traceability. This is a recurring cross-document theme with no synthesis page. A small `concepts/observability` page (or a section in `concepts/correlation-ids.md`) would close the gap.

**Minor — `case.completed` event is never paged.**
- `case.completed` recurs across all three sources and is the central trigger of the pipeline, yet it exists only as inline code text. Per the entity guidance ("central to a document or recurs across sources"), it is a candidate for an `entities/case-completed` page (type `event`/`other`) — or at least a canonical definition. Optional, but note it is currently an unexplained reference for new readers.

**Minor — "platform owner" is an unexplained role.**
- The runbook escalates missing idempotency records "to the platform owner," but no page identifies who/what that is. Acceptable in an internal runbook; flagging only for completeness.

**Linking gaps (not content gaps):**
- `summaries/release-overview.md` lists "durable event log" and "observability" in Related Concepts as **plain text** — "durable event log" should link to `[[concepts/durable-log]]`.
