# Lifecycle Precheck Database Performance

Lifecycle precheck database performance concerns the database workload generated by the Lifecycle Service precheck API during inbound cashflow processing.

## Source finding

In the reported service-isolation tests, 500-cashflow workloads produced database CPU above 90% when lifecycle processing was active. With Lifecycle Service stopped, starting [[orchestration]] after the same inbound workload left CPU below 30%. A separate status-update API test—five batches of 200 updates with orchestration stopped—also remained below 30%.

Under those specific test conditions, the investigation identifies the [[cashflow-lifecycle-service]] precheck API as the leading residual suspect. It does not implicate Lifecycle Service status updates, orchestration, Rule Service, or message-event as direct causes in those tests.

## Evidence boundary

This is an operational elimination result, not a query-level root-cause proof. The source does not provide SQL traces, query plans, buffer statistics, wait events, locks, concurrency levels, cache state, or data-distribution controls. It therefore cannot establish which precheck query caused the CPU load or whether each proposed index was used.

The reported index candidates on `ratan_cashflow_lifecycle_service.ratan_stella_message_event_source` are:

- `settlement_date`, under the potentially misleading name `ratan_stella_message_event_source_trade_id_idx`;
- `originating_trade_id`;
- `(trade_id, major_version)`.

The missing plan-to-index evidence is tracked by [[are-lifecycle-precheck-indexes-proven-by-query-plans]].
