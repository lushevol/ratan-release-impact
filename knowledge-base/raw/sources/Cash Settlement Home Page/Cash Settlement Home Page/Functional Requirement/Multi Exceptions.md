# Multi Exception Generation

When there's new cashflow received in Ratan, it would be published to the settlement workflow and run through the below exception checking logic and decide if we need to tag this exception to the cashflow.

# **Maker/Checker exceptions**

- **Pending Confirmation/Affirmation**: 1. This exception will be generated if both parent trade affirmation/confirmation and cashflow affirmation are missing for the cashflow. 2. Here're the details of trade confirmation status 1. Ratan will read Confirmation Status from below patch. If either trade or cashflow has confirmation status, cashflow will be taken as confirmed | # | Message | Xpatch/Logic Model | Confirmation Status | | --- | --- | --- | --- | | 1 | Stella Trade | Trade_State | NONCONFIRMED|AFFIRMED|CONFIRMED | | 2 | Murex Trade | Source_System_Validation_Status | COMP | | 3 | Stella Cashflow | /scb:SCBML/scb:payload/scb:cashflowPayload/scb:tradeReferenceInformation/scb:state[@stateScheme='[http://www.sc.com/coding-scheme/state/tradeWorkflowStatus](http://www.sc.com/coding-scheme/state/tradeWorkflowStatus)'] - TBD | NONCONFIRMED|AFFIRMED|CONFIRMED | | 4 | Murex Cashflow | /scb:SCBML/scb:payload/scb:cashflowPayload/scb:tradeReferenceInformation/scb:state[@stateScheme='[http://www.sc.com/coding-scheme/state/tradeWorkflowStatus](http://www.sc.com/coding-scheme/state/tradeWorkflowStatus)'] | COMP | 2. If the cashflow come after the trade confirmation status ready in Ratan, the cashflow will query confirmation status from cashflow message first, if not confirmed, then query trade confirmation status with the trade id. 3. If the cashflow come first and when the trade confirmation message is available, Ratan will scan the related cashflows with the trade id(for both Murex and Stella cashflow) and auto remove the cashflow exception if the trade confirmation status is matched( these values above for Murex & FMRP trades respectively) 3. Exception: 'Pending Affirmation' exception should not be triggered for Reversal Cashflow/internal counterparty cashflow. 1. If Cashflow.Cashflow_Event_Reason==Reversal, then do not trigger the exception. 2. If Entity.Counterparty_Is_Internal==Y, then do not trigger exception 4. Exception: 'Pending Affirmation' exception should not be triggered if component cashflow have same trade ID, which is confirmed 5. Maker can fill in affirmation details for submit, checker can only approve or reject the affirmation info that maker filled in, and no access to update affirmation detailed info. 6. The 'Cashflow Affirmation' section is always available in Maker's page (even there's no 'Pending Affirmation') exception. Only when there's 'Pending Affirmation' exception the 'Cashflow Affirmation' is mandatory for Maker's fill in.

- **Missing Vostro: **Vostro is missing, more details can be found in [https://confluence.global.standardchartered.com/display/DSP/FMRP+-+SSI+Stamping+Flow](https://confluence.global.standardchartered.com/display/DSP/FMRP+-+SSI+Stamping+Flow)
- **Multi Vostro: **Multi Vostro stamped on the cashflow, more details can be found in [https://confluence.global.standardchartered.com/display/DSP/FMRP+-+SSI+Stamping+Flow](https://confluence.global.standardchartered.com/display/DSP/FMRP+-+SSI+Stamping+Flow)
- **Nostro vs Vostro Mismatch **: The settlement account & settlement means are different between Vostro & Nostro, more details can be found in [https://confluence.global.standardchartered.com/display/DSP/FMRP+-+SSI+Stamping+Flow](https://confluence.global.standardchartered.com/display/DSP/FMRP+-+SSI+Stamping+Flow)
- **Adhoc SSI: **When settlement ops manually overwrite the system assigned SSI.
- **Missing Nostro: **There's no Nostro defined for particular 'Legal Entity'/'Currency', more details can be found in [https://confluence.global.standardchartered.com/display/DSP/FMRP+-+SSI+Stamping+Flow](https://confluence.global.standardchartered.com/display/DSP/FMRP+-+SSI+Stamping+Flow)
- **Validate Ben Info**: When the payment type is MT202 and the beneficiary BIC is blank.
- **GSAM Client**: 1. Get the counterparty FMID **Entity.Counterparty_SCI_FMID** from cashflow 2. Query SCI API( There's new SCI API to be onboarding in Mar 2023, can check details with Ratan BAU Squad) to get the value legalEntity.operationStatus1Value, if the value is 'REFER' then tag the cashflow as 'GSAM Client'. 3. TODO: Use NSTP reason for the tagging.
- **Back Value**: This should run after the SSI stamping or SSI checker approval. 1. If the settlement means from Vostro is 'Over Account' then end the exception checking process, else continue with the below checks. 2. If cashflow value date (Cashflow.Payment_Date) is < current system date( physical date on the server), then populate this exception. 3. If value date == current system date, if the current system time(GMT) > release cutoff time then populate this exception.
- Bad Business Day: When the payment date is fall in the non business day.
- **Adhoc_Netting: **If the netting is performed on the non netting client ( component cashflow are not holding in 'Pending Netting')Conditions to generate this exception: - Cashflow.Is_Adhoc_Net is true
- **Corporate Client**: The rule would be defined with counterpart FMID/FM Code. 1. Get the counterparty FMID **Entity.Counterparty_SCI_FMID** from cashflow 2. Query SCI API to get the FM Code with FMID, the SCI field is fmAccount.fmType. if client type is 'CORP' then populate this as 'Corporate Client' exception.

# **Checker Only exceptions**

- **Secondary Vostro: **The single Vostro is picked up after the SSI query & best matching rule, more details can be found in [https://confluence.global.standardchartered.com/display/DSP/FMRP+-+SSI+Stamping+Flow](https://confluence.global.standardchartered.com/display/DSP/FMRP+-+SSI+Stamping+Flow)
- **Reversal: **For the post settled trade amendment, the 'Reversal'(or Withdrawal) cashflow would be tagged with this exceptions as part of the multi exception checking. Can rely on the below 2 Ratan logical model fields to store the related information | New Logical model | New Physical model | Sample Values | | --- | --- | --- | | Cashflow.Cashflow_Event_Reason | /scb:SCBML/scb:payload/scb:cashflowPayload/scb:cashflow/scb:header/scb:eventReason[@eventReasonScheme='[http://www.sc.com/coding-scheme/eventReason](http://www.sc.com/coding-scheme/eventReason)'] | - 'Reversal' when the cashflow is to withdrawal the settled cashflow - 'Rebook' when the cashflow is the new cashflow from the post settled trade amendment event (when there's 'withdrawal'/'New' generated on the settled cashflow) - 'Reversal_Rebook' when component cashflow contains any above | | Cashflow.Booking_System_Event | /scb:SCBML/scb:payload/scb:cashflowPayload/scb:cashflow/scb:header/scb:event[@eventScheme='[http://www.sc.com/coding-scheme/event/Booking-System-Event](http://www.sc.com/coding-scheme/event/Booking-System-Event)'] | - New: Cashflow generatred from new trade booking - Amendment: Cashflow generated from trade amendment or any other similar market events - Withdrawal: Cashflow generated from trade cancellation | | Cashflow.Is_Adhoc_Net | /scb:SCBML/scb:payload/scb:cashflowPayload/scb:cashflow/scb:header/scb:isCashflowAdhocNet | - true: If it is manual netting, and not all the component cashflows are Pending Netting - false: otherwise | Conditions to generate this exceptions: - Cashflow.Cashflow_Event_Reason==Reversal
- **Rebook: **For the post settled trade amendment, the 'Rebook'(or New) cashflow would be tagged with this exceptions as part of the multi exception checking. Conditions to generate this exceptions: - Cashflow.Cashflow_Event_Reason==Rebook
- **NetOverAmend: **The netting resultant cashflow** **when ops net the reversal & rebook cashflows. - Cashflow.Cashflow_Event_Reason==Reversal_Rebook - Cashflow.Netting_Id is not null
- **Net Cashflow**: This exception is for the netting resultant cashflow which are netted from the netting client cashflows( cashflows stopped by netting client static data and holding in 'sub status type' == 'Pending Netting')
- **Settled as gross: **The cashflow is in 'Pending Netting'/'Pending Another Leg' but user manually settle these cashflow as Gross.
- **Previously Netted**: Can run after the 'Pending Netting' and 'Auto Netting' exception checking, if the cashflow is not applicable for these 2 exceptions then rely on the below conditions to decide if the cashflow is eligible for this exception. 1. Cashflow.Status_Event_Type == 'Un-Net' 2. Trade.Settlement_Method == 'Gross'
- **Bad Business Day**: 1. There're currency calendar defined in Ratan which is sourcing from RDM 2. Get the payment date Cashflow.Payment_Date and currency Cashflow.Payment_Currency from the cashflow 3. Use the Cashflow.Payment_Currency to query the underlying holiday static data and cross check if the payment date is falling on the holiday.
- **Replayed from Failed Status**: - Settlement Ops perform 'Re-Instate' action on the 'FAILED' cashflow, cashflow status moved from 'FAILED' to 'QUEUED'. - The re-instate 'QUEUED' cashflow are pushed back to workflow and generate this exception.
- **NSTP Exceptions: The cashflow matching with the standard NSTP Rules.** 1. **NSTP Client**: Particular NSTP rule defined with Client FMID/FMCode 2. **NSTP Product**: : Particular NSTP rule defined with Product Type. 3. **NSPP Currency**: Particular NSTP rule defined with Currency.
- **High Value Payment**: Populate this exception if the payment amount is above 100 million in USD. Need to use the FX Conversion API [FX Conversion Service - Functional Specification](https://confluence.global.standardchartered.com/display/FMRP/FX+Conversion+Service+-+Functional+Specification) to calculate the USD amount.
