# Background

As the FMRP Strategy design Stella would be the trade lifecycle engine and take the responsibility of cashflow generation, Ratan as the settlement platform will take the cashflows generated from Stella. As interim stage Ratan would take the cashflow from Murex 2.11 as well, which the booking is still in Murex 2.11. Ratan need to build a strategy cashflow event handling mechanism which can cater for both the target architecture and meanwhile can work with the Murex 2.11(and can have other TP system to integrate) cashflows for the interim period. Given the Murex 2.11 & Stella cashflow behaviour are not exactly the same there would be adaptor layer for the Murex 2.11 cashflow to make it more common and align with the strategy model.

# Key attributes & agreement with Stella/Murex 2.11

As cashflow settlement platform, Ratan need to know what happen in Stella/Murex 2.11 when they populate cashflow. One of the major objective is transaction control which Ratan can handle the cashflows from different trade events properly e.g. cashflow from new trade booking should be handled prior to the cashflows from trade amendment. - Cashflow Events: Only Withdrawal and New cashflow events from Stella and Murex 2.11

# Cashflow Event Control

After the batch management, Ratan can proceed the cashflow with proper transaction sequence. Then we would have the second level management to handle the settlement operation risk. For some case there would be multi cashflow events under same cashflow id( e.g. the trade undo), below are the Ratan event control rules if there're multi events received under same cashflow id.

- New + Withdrawal: Normal business event
- New + Withdrawal + New: This can from the trade undo event, and these 3 cashflow event can be proceeded one by one.
- New + New + New : Only proceed the first new and discard the subsequent new.
