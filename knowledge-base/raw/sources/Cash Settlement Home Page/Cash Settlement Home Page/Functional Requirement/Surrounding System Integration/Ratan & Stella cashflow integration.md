# Background

FMRP Stella is the application to generate cashflow and mange lifecycle in BCS project which is the first implementation under the FMRP design. In the BCS project Stella had taken the responsibility of Netting/Value date update/Suppression which looks more like post trade functionality. There're some new discussion as part of China entity onboarding(Murex decomm), we're going to propose new approach to decouple these functions from Stella and move them to post trade applications. This document will define the new E2E flow with clear responsibility between pre-trade & post trades and illustrate the major business scenarios under the new approach.

# New flow under FMRP

- Stella is responsible to generate cashflow generation: 1. Generate cashflow events New/Amendment/Cancellation from trade business event 2. Stella would generate new business version on the new cashflow to indicate the update from TP system. 3. All cashflow status default as 'Projected', the remaining status would be handled in post trade only 4. Both theoretical & known cashflow would be generated and sent to Ratan
- Cashflow lifecycle(status movement) management will be handled by post trade, status changes are driven by post trade activities 1. Projected → Queued : Ratan move the cashflow status to 'Queued' on VD-5. 2. Queued → Pending : 'Pending' used for NSTP criteria like NSTP Review/CPN/SSI Exception. 3. Pending → Validated : Cashflow moved to 'Validated' after FMO resolve the NSTP criteria. 4. Validated → Released : Swift message generated and sent to FMSRE. 5. Released → Settled: Swift message had been sent to swift network.
- Hard blocking on trade amendment 1. 'Released' and 'Settled' status will be sent back to Stella 2. With cashflow status as 'Released' or 'Settled', trade amendment is blocked for FO. 3. Only MO can amend trade when the underlying cashflow in 'Released' or 'Settled' status, the cashflow template would be 'Withdrawal & New'
- Netting 1. Netting would be handled by post trade application 2. Ratan only update the status of component cashflow to Stella ('Netted')
- Value Date update 1. As new proposal post trade won't update the value date populated by Stella 2. Post trade will add new additional field 'Payment Date' which is updated by FMO in post trade and not touch the 'Value Date' , the current interface to update the value date(by Stella) is not required in target flow 3. The new field 'Payment date' will be used to drive the swift message generation with updated settlement date.
- Filtering Logic - Duplication found based on - Cashflow Id - Business Version - Status_Update Event

# Integration flow

# New changes for Stella & Ratan

- Stella: New status moving actions 1. Projected → Released 2. Projected → Netted 3. Netted → Projected 4. Netted → Released 5. Netted → Settled
- Ratan: 1. Materialization 2. Netting resultant cashflow generation 3. Auto un-net
- Version related fields 1. Business Version : Managed by FMRP Stella, starting with 0 when there's new cashflow generated and will increase from the amendment/withdrawal events. 2. Cashflow Version : Managed by FMRP Stella, starting with 0 and increase when there's new cashflow message generated( e.g. when there's status update) 3. Ratan Minor Version : Generated by Ratan, associated with particular business version. Starting with 0 and would increase to record the result from any Ratan internal new activities( workflow & FMO GUI actions), will be reset to 0 when there's new business version populated by Stella.
