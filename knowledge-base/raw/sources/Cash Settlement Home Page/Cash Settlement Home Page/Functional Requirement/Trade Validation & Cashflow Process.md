# Background

For the major TP systems(FMRP Stella/Murex 2.11) the cashflow can be generated when the trade is booked even before the trade is validated, as requested by settlement ops the cashflows can only be visible for them after MO done the trade validation.

# Problem Statement In the current FMRP strategy

- Only after the trade( particular market event) is validated then the underlying cashflows would be visible for settlement opsAFFIRMED
- Cashflows from Murex 2.11: There's trade validation process in Murex 2.11, but there's no control from Murex 2.11 that only sending cashflows to RATAN post trade validation.

# Principle of Strategy Approach

- Only after the trade( particular market event) is validated then the underlying cashflows would be visible for settlement ops
- For the non economic trade amendment validation, if there’s **no manual action performed**(considering historical actions as well) or **cashflow not released/settled** RATAN would reflect the latest cashflow id in cashflow blotter. The in scope user manual action list is as below. 1. Exception Fix/Reject( affirmation/SSI key in/swift value date key in/approve/reject) 2. Settle as Gross 3. Netting/un-net 4. Hold/Unhold 5. Manual fail 6. Re-Instate 7. FM Comment 8. Manual Cashflow Suppression 9. Manual Swift Suppression 10. Early materialization

# Target function flow: Cashflow Process VS Trade Validation

- Cashflow generated by Stella/Murex 2.11 and sent to RATAN, these cashflows can be from trade which are not validated yet.
- When received these cashflows, RATAN will check the parent trade validation status. If the trade is not validated RATAN will hold these cashflows in the settlement process, cashflows won't be visible from GUI for settlement ops.
- Trade validation process would driven by MO and trade validation status would be sync to TDS3.
- RATAN then would take the trade validate status from TDS3 and lookup the impact cashflows to resume the settlement process.
